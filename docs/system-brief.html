System brief · September 2026

Inside Nightingale

A first-touch-to-care system for Malaysian private clinics. A stranger with a frightening symptom gets real help in seconds without giving up their name — and when they choose to be known, nothing they said is lost and nothing unsafe is hidden.

Jason Ong Yann Jing Sunway University · Data Analytics nightingale-ai-drab.vercel.app

The premise

Asking is not diagnosing

Most clinic chatbots answer questions and try very hard not to diagnose. Nightingale inverts that. It asks the questions a clinician would ask — and stops there.

“Does the pain spread to your arm?” gathers a fact. “That suggests cardiac ischaemia” draws a conclusion. The system does the first and hard-blocks the second, which leaves the conclusion with the clinician — exactly where the Medical Act 1971 puts it.

That single decision pays off four ways. It is non-diagnostic by construction rather than by instruction. The questioning is the value the guest receives, so there is no dead air while the system “collects information”. It produces a structured record a nurse can act on instead of a chat transcript. And it gives a frightened person a bounded task rather than an open-ended interrogation.

A confirmation is a promise. Only make it if the write happened.

Request lifecycle · in order

What happens when someone types one sentence

This is the part that makes it a system rather than a wrapper around a language model. Nine stages run on every message, and only two of them involve the model at all.

  1. 1

    Redaction

    Names, NRIC and passport numbers, phone numbers and emails are stripped before anything else sees the text. Recall is biased over precision: it would rather over-redact than let an identifier through. Validation acts as a confidence signal, never a gate — an NRIC that fails its checksum is still redacted.

  2. 2

    Deterministic risk gate

    16 rules and 171 phrase variants across English, Malay, Indonesian and Manglish. Runs before the model and never depends on a network call. Context guards handle negation, third-party mentions and historical framing, each with a hard floor so “my father had chest pain” cannot be talked down to nothing.

  3. 3

    Model classification

    A second opinion from the LLM, running in parallel with the reply.

  4. 4

    Merge — the safety property

    The final level is MAX(deterministic, model). The model can raise the risk level. It can never lower it. If the model is unreachable, rate-limited or wrong, the deterministic floor still holds.

  5. 5

    Grounded reply

    Generated against 44 chunks of clinic corpus with character offsets preserved, so a citation resolves to a real span rather than a plausible paraphrase.

  6. 6

    Output guard

    54 banned phrases across 6 categories, checked after generation. The prompt is a request; this is the enforcement. A model that ignores its instructions still cannot ship a diagnosis.

  7. 7

    History engine

    Six complaint frames — pain uses SOCRATES — each field carrying a stated reason for being asked. Only high risk halts the checklist; medium continues, because a medium-risk halt made the system repeat one sentence for five turns.

  8. 8

    Persistence

    Redacted text only. The placeholder-to-original map is deliberately never stored, which means a saved message cannot be un-redacted later, by anyone. That costs a clinician some detail and is the correct trade.

  9. 9

    Funnel event

    A PHI-free row describing what happened, not what was said. This is what the dashboard reads, and why funnel data can be kept 30 days while guest conversations are destroyed at 7.

Infrastructure

Supabase and Vercel, and why the split matters

Supabase — the enforcement boundary

Supabase is managed Postgres, and it is doing considerably more than storage. The access rules live inside the database as 23 Row Level Security policies, default-deny.

That distinction is the whole point. An application-level check is something a future route can forget to call. An RLS policy is something no route can bypass, because the refusal happens in Postgres. The access-control tests authenticate as a patient and query the database directly — if RLS were removed, every route could still look correct and those tests would fail immediately.

It also holds the append-only living profile (facts supersede, never overwrite), the guest-to-patient conversion path, and the 7-day retention schedule for guest data.

Vercel — the runtime and the gate

Vercel hosts the Next.js application: 14 serverless API routes, four pages, and the edge proxy that runs before any of them.

That proxy is where staff authentication happens. It gates /dashboard and /clinician — and, critically, the API routes behind them. Gating the page while leaving /api/analytics open would be theatre: same data, one fetch away from anyone reading the page source.

Vercel also holds the secrets. The service_role key lives only in server environment variables; it bypasses RLS entirely, so it must never reach a browser. The public anon key is safe there by design, because RLS is what actually restricts it.

Why two keys, not one

The browser gets the anon key and sees only what policy allows. The server gets the service key and sees everything. If those were the same key, every RLS policy in the schema would be decoration. The naming rule matters too: a NEXT_PUBLIC_ prefix ships a variable to the browser, so prefixing the service key would silently publish the master key to every visitor.

The ordering is the product

The queue sorts high medium low by clinical risk. It would be trivial to sort by predicted commercial value instead, and it would make a better sales tool and a worse clinical one — a real emergency sitting at position 31 behind thirty price enquiries. Nothing in the analytics layer is permitted to touch that ordering.

Machine learning

Where the FYP methodology went

Two distinct layers, and neither of them is the language model. The LLM is a component the system constrains; the machine learning is what measures and predicts around it.

Layer one — evaluation as measurement, not vibes

The safety gate is treated as a classifier and evaluated like one. Wilson confidence intervals on every rate, subgroup breakdowns, and the four-fifths rule — the disparate-impact test from employment law — applied to a safety property rather than a hiring decision.

This found something real. Emergency detection worked in English and Malay but degraded badly in Indonesian, giving an adverse-impact ratio of 0.768 — well below the 0.8 threshold. The cause was a single orthographic difference: Malay sesak nafas against Indonesian sesak napas. An Indonesian speaker describing breathlessness was less likely to be escalated than a Malay speaker describing the same emergency.

The second row came from the same audit. Words like clinic, doctor and hospital were treated as clinical signal, so “what are your opening hours” triggered a fail-closed floor. Removing them cost nothing and stopped the system crying wolf at people asking about parking.

Layer two — abandonment prediction

This is the FYP churn methodology pointed at a different outcome. Churn asks will this customer leave? This asks will this person give up before reaching a clinician? — structurally identical, and the class imbalance, leakage traps and fairness questions all carry over.

Three methodological choices are doing the work here, and each corresponds to a way this kind of model usually goes wrong.

  • Leakage is named, not merely avoided. Message count and history completeness are excluded and listed explicitly in the code. Including them would produce a beautiful AUC and a useless model, because long conversations are the ones that converted.
  • PR-AUC is the headline, not ROC-AUC. With an imbalanced label, ROC-AUC flatters. Brier score is reported too, because the output is meant to be read as a probability by a person rather than thresholded by a machine.
  • The model audits itself for fairness. It runs the same four-fifths test on its own per-channel error rates — and when it returned 0.639 from a group of 16, it labelled the result underpowered rather than reporting a disparity that noise alone could produce.
The constraint that defines its use

This model finds steps that lose people, so the product can be fixed. It does not rank patients, and its output must never influence the order of the triage queue. A model saying “social-comment arrivals at 2am abandon at 80%” is an instruction to improve the after-hours message — not a licence to deprioritise those people.

What the numbers above are worth

92% of that training data is synthetic, generated with distributions that were chosen rather than measured. Those figures validate that the pipeline runs end to end; they are not evidence about real patients. Every synthetic row is tagged, the API reports how many rows sit behind each number, and the dashboard states it above the figures rather than in a footnote.

Engineering posture

Three rules that shaped the code

Fail closed, but scoped

When the classifier fails, risk floors at medium — but only for messages carrying clinical signal. An early version floored every message at medium, which would have buried real emergencies in a queue of people asking about parking.

Never overwrite

Facts supersede rather than replace. A patient contact is a row, not a column, so an email can change without breaking history. A clinician's reply is a new record, never an edit to the escalation.

Honest failure beats quiet success

Every failure path in the product was honest; the success path was the one that lied. “Sent to the clinical team” printed unconditionally while nothing was being stored. It now requires proof of the write, and a schema bug that made guest escalations impossible was found because of it.

Prove it over HTTP

The tests run against the real running server, not mocks. What matters is what leaves the process, not what a helper returns — and only a real request against real RLS can prove Patient A cannot read Patient B.

Limitations

What this is not

  • Synthetic throughout. No real clinic, no real doctors, no real patients. The clinic corpus, the traffic and the training data are all generated.
  • One shared admin password. Appropriate for a single operator, wrong for a clinic: no per-person identity, so nothing attributes to a human in the audit log, and revoking one person means changing it for everybody. Supabase Auth with is_care_team() is the real answer, and the schema already assumes it.
  • The abandonment model is untrained on reality. It is labelled as such everywhere it appears, and must be re-run before any figure from it is quoted.
  • Not a medical device. It is non-diagnostic by construction, and the escalation path assumes a human clinician is on the other end.
